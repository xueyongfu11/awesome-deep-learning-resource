# Decode 与 CUDA Graph

## 1. CUDA Graph 解决的问题

普通执行通常由 CPU 逐个提交 GPU kernel。Decode 中短 kernel 较多时，下发开销可能形成 GPU 空洞。CUDA Graph 记录设备操作及依赖，实例化后通过整体重放降低重复提交成本。

它本身不等于算子融合，也不直接减少模型计算量；输入准备、图启动和设备计算仍然存在。

## 2. 并发不在捕获档位列表中

以 vLLM 的常见机制为例，未精确命中档位不代表立即退回 eager。框架可以向上选择最近的可用档位，补齐输入后重放。

假设捕获档位为 `[1, 2, 4, 8, 16, 32]`：

| 本轮实际 batch 大小 | 常见处理                           |
| ------------------- | ---------------------------------- |
| 8                   | 直接使用 8 档                      |
| 10                  | padding 到 16，使用 16 档          |
| 20                  | padding 到 32，使用 32 档          |
| 40                  | 超出覆盖范围，通常使用非图执行路径 |

补齐槽位由占位输入和相应元数据处理，最终只使用真实请求的输出。padding 可能增加计算，换取较低的下发开销。

需要区分客户端并发和本轮调度后的执行规模。普通 Decode 每条序列生成一个 token 时，序列数与 token 数接近；推测解码、混合 batch 等场景不能直接等同。

档位匹配和 padding 属于框架策略，不是 CUDA API 自动提供的行为。除了规模，还可能需要匹配 batch 组成、执行模式及后端约束。

## 3. “捕获不到”的两种含义

### 捕获过程失败

可能原因包括：

- 捕获期间出现不允许的同步，例如 `cudaDeviceSynchronize()`，或读取 GPU 标量到 CPU 所触发的同步。
- 算子或库内部使用了不支持捕获的 API、分配方式或执行路径。
- 捕获内外形成不合法的 stream/event 依赖。
- 显存等资源不足，多档位捕获可能增加资源占用。

违规操作可能使捕获失效，结束捕获时无法返回有效图。不能笼统地认为所有内存分配或所有跨 stream 操作都不支持，具体要看 API 和依赖是否合法。

依赖 GPU 数据的任意 CPU 分支也不能自动成为每次重放都会执行的逻辑。常见处理是改写执行路径、将判断移到适当位置，或使用框架及运行时支持的专门机制。

### 捕获成功，但本轮没有可用图

例如 batch 超过最大档位，或者当前 batch、后端和执行模式不满足已捕获图的条件。框架可能选择完整图、分段图或无图路径。

## 4. 后果

| 情况                 | 后果                                            |
| -------------------- | ----------------------------------------------- |
| padding 后重放       | 仍享受图启动优势，但有额外计算                  |
| 分段图执行           | 部分操作重放，其余操作单独执行                  |
| 无图执行             | 逐 kernel 提交，可能增加 token 间延迟、降低吞吐 |
| 捕获异常未被框架处理 | 可能导致初始化失败或请求失败                    |

运行时正常选择无图路径，与捕获报错是两回事。捕获异常不保证自动降级；无图执行的性能损失也取决于原负载是否受 CPU 下发限制。
