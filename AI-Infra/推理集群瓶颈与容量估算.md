# 推理集群瓶颈与容量估算

**峰值每秒到达 20 个请求，需要部署几个副本？** 假设一个副本能稳定处理 4 请求/s，平时计划用到其能力的 70%，答案是 **8 个独立副本**。估算中最需要验证的数字是“4 请求/s”：它取决于请求有多长，以及用户能接受多大的延迟。

下面用同一组假设数据走完估算。一个副本指一套能独立服务请求的模型实例，可以跨多张 GPU。

## 1. 定义要承接的流量

| 请求类型 | 流量占比 | 输入 token/请求 | 输出 token/请求 |
| -------- | -------: | --------------: | --------------: |
| 短请求   |      80% |             500 |             100 |
| 长请求   |      20% |           3,000 |             600 |
| 加权平均 |     100% |           1,000 |             200 |

算例假设请求之间没有共享前缀。压测时按表中比例发送长短请求，保留输入与输出长度的配对。回放生产流量时，还应保留真实到达间隔和前缀复用情况。

**什么算达标？** 本例从客户端测量，使用以下三个条件：

- **首 token 等待时间（TTFT）**：从发送请求到收到首个 token，P95 ≤ 800 ms。
- **每个后续 token 的平均耗时（TPOT）**：对输出至少两个 token 的请求，用首末 token 时间差除以输出间隔数，再对各请求取 P95，要求 ≤ 50 ms。
- **失败率**：失败或超时的请求合计占全部发起请求的比例 ≤ 0.1%。

P95 表示约 95% 的样本落在该值以内。长短请求应分别查看尾延迟。如果用户反馈“生成到一半卡住”，再看相邻 token 的间隔（ITL）：单次长停顿可能被整条请求的 TPOT 平均掉。客户端合并输出时，还要区分响应块间隔和 token 间隔。

## 2. 用显存估算并发范围

模型生成时，要把已处理 token 的注意力键和值保存在显存里，称为 **KV 缓存**。先算每张卡能留给 KV 多少空间，再估算同时在跑的请求会占多少。

```text
每卡 KV 预算 = 总显存 − 权重 − 运行时与临时空间 − 安全预留
单请求完整 KV 字节数 ≈ 2 × 层数 × 已缓存 token 数 × KV 头数 × 每头维度 × 每元素字节数
```

第二式适用于普通 MHA/GQA，系数 2 代表键和值。多卡部署按每张卡实际分片或复制的 KV 计算。MLA、滑动窗口、混合注意力和压缩或量化缓存需按实际存储布局换算。

**怎么从请求速率推到显存？** 稳定运行时，按 Little 定律，平均活跃请求数约等于到达率乘以平均活跃时间（不含排队）。例如每秒进入执行阶段 4 个请求，每个平均活跃 5 秒，就有约 20 个请求同时占用 KV。

实际预算可定期采样每张卡正在使用的物理块。这样能计入分页取整、生成过程中 KV 增长，以及长请求驻留更久的影响。共享前缀对应的物理块只计一次。平均值用于粗估，还要检查高峰时是否出现缓存抢占。

## 3. 测出单副本能稳定接多少请求

**第一轮：固定并发，找性能拐点。** 固定硬件、模型精度、引擎版本、并行和批处理配置，预热后逐档增加并发。以下是示例结果。

| 活跃并发 | KV 占用 | 吞吐       | 延迟达标 |
| -------- | ------- | ---------- | -------- |
| 20       | 10 GB   | 3 请求/s   | 是       |
| 40       | 20 GB   | 5 请求/s   | 是       |
| 60       | 30 GB   | 6 请求/s   | 否       |
| 80       | 40 GB   | 6.2 请求/s | 否       |

从 40 加到 60 并发，吞吐从 5 升到 6 请求/s，延迟却已超标。值得细测的区间就在这两档之间。

**第二轮：固定到达率，验证在线容量。** 固定并发测试中，客户端通常等一个请求结束才补发下一个。服务变慢，客户端也会放慢发压。线上流量仍会继续到达，因此要让压测端独立按目标速率发送请求。

| 到达率     | 重复观察 30 分钟窗口的结果       | 用于规划       |
| ---------- | -------------------------------- | -------------- |
| 4 请求/s   | 延迟、失败率达标，队列无持续增长 | 采用           |
| 4.5 请求/s | 等待队列持续增长                 | 超过已验证容量 |

记录发起、成功完成、拒绝和超时的请求数，同时统计每秒成功完成且满足延迟门槛的请求数。可用同一批完成请求核对单位：800 输出 token/s ÷ 200 输出 token/请求 = 4 请求/s。

## 4. 算副本数，再用集群回放验收

```text
单副本计划承载 = 4 × 70% = 2.8 请求/s
独立副本数 = 峰值请求速率 ÷ 单副本计划承载，向上取整
           = 20 ÷ 2.8，向上取整为 8
```

70% 是本例为波动保留的余量。若还要求一个副本故障后仍按相同比例承接峰值，就部署 **9 个**。若多个副本共用节点或专家并行通信组，应按一次故障实际损失的整组能力计算。

在集群入口回放峰值和突发，检查客户端延迟、失败率及各副本队列。比较集群达标吞吐与“副本数 × 单副本达标吞吐”，查看共享链路、入口或路由不均造成的损失。依赖自动扩容时，回放需覆盖流量上升到新副本就绪的过程，确认积压能排空。

## 集群未达标时，先查哪一段？

先在同一时间窗对比各副本的等待请求、待处理 token、活跃序列、KV 占用和吞吐。少数副本积压时，先查流量分配；普遍积压时，挑代表性实例抓时间线，区分计算、显存访问、通信、主机调度与缓存搬运。下面三种现象可以分别验证。

### 首 token 等得久

把 TTFT 拆成排队、处理输入（Prefill）以及可能的 KV 加载或传输。若主要耗在排队，比较各副本待处理的输入 token 数：即使请求数相同，长输入集中的副本也可能先拥塞。保持流量不变，只改路由，观察热点队列、前缀命中和集群 TTFT 是否一起改善。

### 生成过程中频繁停顿

查看实际使用的 KV 块、抢占次数、重算和 ITL 是否同时上升。固定请求样本，降低活跃并发上限。如果抢占减少、ITL 下降，再看排队是否变长，以判断端到端收益。

### MoE 某一步特别慢

在同一步、同一层，对齐各专家收到的 token 数，以及各并行进程（rank）在分发、专家计算、结果合并三个阶段的耗时。一个 rank 晚到同步点，其他 rank 的等待也可能计入通信时间。

若慢 rank 集中了热门专家，可比较调整专家放置前后的最慢 rank 耗时。若各 rank 负载接近，沿时间线检查跨节点传输、链路争用，以及通信是否与计算重叠。每次只改一个变量，在相同延迟目标下复测。

## PD 分离时，单独算链路容量

Prefill 处理输入，Decode 逐步生成输出。两者分开部署时，请求还需把 KV 从 Prefill 侧传到 Decode 侧。沿用前面的峰值流量，分别计算三段需求：

| 环节    | 每秒需求                        | 假设可用能力                | 估算结果           |
| ------- | ------------------------------- | --------------------------- | ------------------ |
| Prefill | 20 × 1,000 = 20,000 输入 token | 每个实例 8,000 输入 token/s | 至少 3 个实例      |
| Decode  | 20 × 200 = 4,000 输出 token    | 每个实例 1,000 输出 token/s | 4 个实例，恰好满载 |
| KV 传输 | 20 × 64 MiB = 1,280 MiB        | 链路有效带宽 1,024 MiB/s    | 最多 16 请求/s     |

**这组配置最先用尽的是链路带宽。** 每请求平均跨链路传 64 MiB，1,024 ÷ 64 = 16 请求/s。要接住 20 请求/s，应先补足传输能力，再复测排队、KV 交接时间和客户端 TTFT。

实际部署时，Prefill 按前缀复用后真正执行的输入 token 计量，Decode 按目标上下文长度和并发实测。多条链路则按流向分别核对实际传输字节数和有效带宽。
